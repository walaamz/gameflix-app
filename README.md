# GameFlix — User Authentication API

## Project Overview

GameFlix is a game subscription platform developed as part of my software development coursework. This implementation focuses on user registration, login, and secure access to account information using Spring Boot, Spring Security, JWT authentication, and MySQL.

## Technologies Used

- Java 21
- Spring Boot 4.1.1
- Spring Security
- Spring Data JPA / Hibernate
- MySQL
- JSON Web Tokens (JJWT)
- Maven
- Postman

## API Endpoints

| Method | Endpoint | Description |
|---|---|---|
| POST | `/api/auth/register` | Register a new user |
| POST | `/api/auth/login` | Authenticate a user and generate a JWT |
| GET | `/api/users/me` | Retrieve the authenticated user's profile |

### Registration

Accepts an email and password. The password is hashed before being stored in MySQL.

- `201 Created` — Registration successful
- `400 Bad Request` — Invalid registration input
- `409 Conflict` — Email already registered

### Login

Verifies the submitted credentials against the stored BCrypt password hash.

- `200 OK` — Login successful; returns a signed JWT
- `401 Unauthorized` — Invalid email or password

### User Profile

Requires a valid JWT in the `Authorization: Bearer <token>` header.

- `200 OK` — Returns the authenticated user's ID and email
- `401 Unauthorized` — Missing, expired, or invalid token

## Database Configuration

The application uses a MySQL database named `gameflix`.

Create the database before running the application:

```sql
CREATE DATABASE IF NOT EXISTS gameflix;
```

The application reads database credentials from environment variables:

- `MYSQL_USER`
- `MYSQL_PASSWORD`

Hibernate uses `spring.jpa.hibernate.ddl-auto=update` to create and update the database schema during development without deleting existing records.

The `users` table contains an automatically generated ID, a unique email address, and a password column containing the encoded password hash.

The database enforces email uniqueness to prevent duplicate accounts.


### Database Schema

The following schema was generated by Hibernate and verified using `SHOW CREATE TABLE users;` in MySQL Workbench.

```sql
CREATE TABLE `users` (
  `id` bigint NOT NULL AUTO_INCREMENT,
  `email` varchar(255) NOT NULL,
  `password` varchar(255) NOT NULL,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_users_email` (`email`)
) ENGINE=InnoDB AUTO_INCREMENT=2 DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;
```


## Security Implementation

### Password Hashing

Passwords are hashed using BCrypt with a work factor of 12. BCrypt is an adaptive password-hashing algorithm that makes password guessing more computationally expensive.

Passwords are never stored in plaintext or returned in API responses.

### JWT Authentication

After successful login, the application generates a signed JWT containing the user's email as its subject.

Tokens expire after one hour. This limits how long a compromised token can be used.

The server validates token signatures and expiration dates before granting access to protected endpoints.

JWT payloads are encoded rather than encrypted, so sensitive information such as passwords is not included in token claims.

### API Security

- Registration and login are publicly accessible.
- The user profile endpoint requires authentication.
- Invalid login credentials return the same generic error message.
- CORS is restricted to `http://localhost:5173`.
- The application uses stateless authentication.

## Running the Application

1. Install Java 21, Maven, and MySQL.
2. Create the `gameflix` database.
3. Configure `MYSQL_USER`, `MYSQL_PASSWORD`, and `JWT_SECRET` as environment variables in IntelliJ.
4. Set `JWT_SECRET` to a securely generated Base64-encoded 32-byte random key.
5. Run `GameflixApplication.java`.
6. Use Postman to test the endpoints at `http://localhost:8080`.

The JWT secret and database credentials are not hardcoded in the application.

## Changes From Module 3 Design

The Module 3 design originally proposed endpoints such as `POST /users`, `POST /login`, and `GET /users/{id}`.

For this implementation, I organized the authentication endpoints under `/api/auth` and changed the profile endpoint to `/api/users/me`.

This allows the application to identify the user through their validated JWT instead of accepting an arbitrary user ID in the URL.
